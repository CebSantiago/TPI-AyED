# TRABAJO PRÁCTICO INTEGRADOR (TPI) – AyED 2026

El presente Trabajo Práctico Integrador (TPI) tiene como finalidad integrar y aplicar los contenidos desarrollados en la asignatura Algoritmo y Estructura de Datos mediante la resolución de un problema basado en una organización realista.

La propuesta se articula con el caso de estudio del teatro CaPaz S.A., utilizado en la asignatura Sistemas y Procesos de Negocio. En dicho caso, la organización necesita mejorar la gestión de su cartelera, la disponibilidad de ubicaciones, la comercialización de entradas y la generación de información para la toma de decisiones.

Desde Algoritmo y Estructura de Datos, cada equipo deberá diseñar e implementar una aplicación de consola que resuelva un conjunto delimitado de problemas relacionados con esa actividad.

El objetivo no es desarrollar un sistema comercial completo, sino construir una solución funcional que permita demostrar el dominio de los contenidos de la materia, la capacidad de analizar problemas y la correcta selección e implementación de algoritmos y estructuras de datos.

La solución deberá funcionar correctamente y, además, sus integrantes deberán ser capaces de explicar y justificar las decisiones tomadas durante el desarrollo.

Para este trabajo se implementará únicamente un prototipo académico. No se requiere desarrollar una interfaz gráfica, una página web, una base de datos, una plataforma de pagos ni un sistema de autenticación real.

La información podrá almacenarse en estructuras de datos en memoria y/o archivos y cargarse mediante datos de prueba definidos por el equipo.

## RF1. Gestión y consulta de funciones

Cada función deberá contar, como mínimo, con los siguientes datos:

- Código identificador.
- Nombre de la obra o espectáculo.
- Fecha.
- Horario.
- Sala.
- Precio de platea.
- Precio de palco.

La aplicación deberá permitir:

1. Registrar una nueva función.
Creo que taria 2. Consultar todas las funciones registradas.
Creo que taria 3. Buscar una función por su código.
Creo que taria 4. Buscar funciones mediante el nombre completo o parcial de la obra.
5. Mostrar un mensaje apropiado cuando no existan coincidencias.
6. Ordenar las funciones según un criterio definido por el equipo, por ejemplo, nombre de la obra o fecha.

El equipo deberá explicar cómo se almacenan las funciones y por qué eligió esa representación.

## RF2. Representación y consulta de ubicaciones

Cada función tendrá ubicaciones disponibles para la venta.

La aplicación deberá representar las ubicaciones de ambos sectores y distinguir, como mínimo, entre los estados disponible y vendida.

Se deberán cumplir las siguientes condiciones:

1. La platea deberá contemplar 350 ubicaciones.
2. Los palcos deberán contemplar 250 ubicaciones.
3. Cada ubicación deberá tener un identificador único dentro de su sector y función.
4. El programa deberá permitir consultar las ubicaciones disponibles.
5. No se podrá vender una ubicación que ya haya sido vendida.
6. La disponibilidad de una función no deberá confundirse con la disponibilidad de otra función.

## RF3. Registro de ventas

El programa deberá permitir registrar una venta asociada a una función.

Cada venta deberá incluir, como mínimo:

- Número o código de venta.
- Código de la función.
- Sector.
- Número de ubicación.
- Cantidad de entradas.
- Precio aplicado.
- Descuento, si corresponde.
- Importe final.

El prototipo deberá permitir registrar la venta de una o más entradas, siempre que las ubicaciones estén disponibles.

Se deberán implementar las siguientes reglas:

1. Verificar que la función exista.
2. Verificar que las ubicaciones seleccionadas sean válidas.
3. Comprobar que todas las ubicaciones solicitadas estén disponibles antes de confirmar la venta.
4. Evitar vender dos veces una misma ubicación.
5. Calcular el importe de la operación.
6. Aplicar un descuento del 30 % cuando el comprador sea socio habilitado, según el criterio de elegibilidad definido para el prototipo.
7. Actualizar la disponibilidad solamente cuando la venta haya sido validada.
8. Registrar la operación en un archivo persistente, para su posterior consulta.

Para simplificar el alcance, no se implementarán pagos electrónicos reales ni la gestión completa de cuotas de socios.

## RF4. Consultas y reportes

La aplicación deberá generar información que permita analizar las ventas.

Se deberán implementar, como mínimo, las siguientes consultas:

1. Cantidad de entradas vendidas para una función.
2. Cantidad de ubicaciones disponibles para una función.
3. Recaudación total de una función.
4. Recaudación total de todas las funciones.
5. Listado de funciones ordenado según un criterio de demanda.
6. Identificación de la función con mayor cantidad de entradas vendidas.

El equipo deberá definir cómo se resuelven los empates y qué ocurre cuando todavía no existen ventas registradas.

Los cálculos deberán realizarse a partir de los registros almacenados. No se aceptarán resultados escritos manualmente ni valores previamente calculados que no reflejen las operaciones realizadas.

# Contenido Obligatorio

Todos los contenidos de esta sección deberán estar presentes en la solución y correctamente justificados.

## Vectores

El programa deberá utilizar un vector para almacenar y administrar un conjunto de elementos homogéneos del problema.

Por ejemplo, podrá utilizarse para representar funciones, ventas o códigos de identificación.

Se deberá implementar el recorrido del vector para realizar al menos una operación de consulta o procesamiento.

En el informe se deberá indicar:

- Qué información se almacena.
- Cómo se accede a sus elementos.
- Qué operación se realiza mediante el recorrido.
- Qué sucede cuando el vector está vacío o cuando se busca un elemento inexistente.

## Matrices

Se deberá utilizar una matriz para representar las ubicaciones de una función.

El equipo deberá implementar operaciones de recorrido y consulta sobre la matriz.

Se deberá poder determinar el estado de las ubicaciones y contabilizar las disponibles y las vendidas.

La implementación deberá contemplar los límites de filas y columnas y evitar accesos fuera de rango.

Durante la defensa oral, los integrantes deberán explicar cómo se relacionan los índices de la matriz con las ubicaciones físicas.

## Búsquedas

Se deberá implementar manualmente al menos un algoritmo de búsqueda estudiado en la materia.

Como mínimo, se deberá utilizar para localizar una función por su código.

El informe deberá incluir:

- Nombre del algoritmo utilizado.
- Pseudocódigo o descripción de sus pasos.
- Condición de finalización.
- Tratamiento del caso en que el elemento no existe.
- Análisis de la cantidad de comparaciones que puede realizar.

No se aceptará reemplazar la implementación requerida por una búsqueda incorporada en una biblioteca o por un método que oculte el algoritmo.

Si el equipo incorpora una búsqueda binaria, deberá garantizar que los datos estén ordenados según el mismo criterio utilizado para buscar.

## Ordenamientos

Se deberá implementar manualmente al menos un método de ordenamiento estudiado durante la cursada.

El método se utilizará para ordenar funciones, ventas o resultados de consultas.

El equipo deberá explicar:

- Qué criterio de ordenamiento seleccionó.
- Qué algoritmo implementó.
- Cómo funciona el algoritmo sobre los datos utilizados.
- Qué sucede cuando dos elementos tienen el mismo valor según el criterio de ordenamiento.
- Cuántas comparaciones o iteraciones se realizan en un ejemplo concreto.

No se permitirá utilizar `sort()` ni `sorted()` para resolver el ordenamiento obligatorio.

La aplicación podrá incorporar otras herramientas auxiliares, pero deberá ser posible identificar y evaluar la implementación propia del algoritmo solicitado.

## Funciones y modularización

La solución deberá dividirse en funciones con responsabilidades claras.

Se deberá evitar concentrar toda la lógica en un único bloque de código o en una única función principal.

No se aceptará dividir artificialmente el código en funciones que no aporten claridad ni reutilización.

## Cadenas de caracteres

Se deberán utilizar cadenas de caracteres para procesar información textual del problema.

Como mínimo, el programa deberá permitir buscar obras por nombre completo o parcial, sin distinguir entre mayúsculas y minúsculas.

El equipo deberá explicar qué tratamiento realiza sobre las cadenas para efectuar la búsqueda y cómo evita resultados incorrectos ante entradas vacías o nombres que no existen.

Se deberán incorporar al menos dos pruebas específicas relacionadas con cadenas de caracteres.

## Recursividad

Se deberá implementar al menos una función recursiva que resuelva un problema real del prototipo.

No se aceptará una función que invoque recursividad sin que esta sea necesaria para resolver el problema.

## Estructuras dinámicas lineales

El equipo deberá implementar y utilizar una estructura dinámica lineal estudiada en la materia.

La estructura seleccionada deberá cumplir una función concreta dentro del prototipo. No será suficiente implementarla sin utilizarla o incluirla únicamente como demostración.

La implementación deberá contemplar las operaciones propias de la estructura seleccionada, así como las situaciones de estructura vacía y los casos límite correspondientes.

No alcanza con utilizar una lista nativa de Python y denominarla estructura dinámica lineal.

## El equipo deberá entregar:

1. Informe con explicación de las estructuras de datos utilizadas.
2. Explicación de los algoritmos de búsqueda y ordenamiento.
3. Desarrollo del problema recursivo, con caso base y caso recursivo.
4. Justificación de la estructura dinámica lineal seleccionada.
5. Análisis de las limitaciones de la solución.
6. Conclusiones del trabajo.
7. Bibliografía y declaración de herramientas utilizadas, incluidas las herramientas de inteligencia artificial, si corresponde.

La entrega final deberá demostrar la integración de los contenidos obligatorios y la correcta ejecución de las funcionalidades principales.

# Presentación y defensa oral

La defensa oral es una instancia obligatoria de evaluación individual dentro de un proyecto grupal.

Cada equipo realizará una exposición del trabajo y una demostración del programa.

Posteriormente, cada integrante deberá responder preguntas del docente y demostrar que comprende el código desarrollado.

La exposición deberá centrarse en las decisiones técnicas y algorítmicas, no solamente en la descripción del sistema.

El docente podrá asignar a cada integrante una pregunta conceptual, un fragmento de código o una modificación breve relacionada con cualquiera de los contenidos obligatorios.

El docente podrá solicitar una modificación no anticipada durante la defensa oral para comprobar que los estudiantes comprenden la solución.
